RestoreProof — Product & Implementation Plan

RestoreProof is a Dockerized, community-edition Proxmox restore-drill appliance (Ubuntu LXC host) that uses the Proxmox API (SSH only for screenshots), runs one full restore→boot→screenshot→cleanup cycle at a time from PBS backups, and emails results—with a modern dual-theme admin UI and a clear backlog for paid/community upgrades.

Product summary

RestoreProof is a self-hosted restore-verification tool for Proxmox. Admins deploy it as Docker on an Ubuntu LXC, connect one or more Proxmox API endpoints (standalone host or cluster node), and run automated non-destructive restore drills: restore latest PBS backup to a temporary ID, detach NICs, boot, screenshot, cleanup, email, and show proof in the UI.

Positioning: Free community edition (open source) with a documented path for future paid extras—no paid features in v1.

Docker image (planned): hesseltined/restoreproof (compose-first install).

Architecture

Admin Browser → RestoreProof Web → RestoreProof API → Postgres ↘ Restore Worker → Proxmox API → PBS → Proxmox SSH/QMP → SMTP

Runtime (Docker Compose):

  • web — React + Vite + TypeScript SPA
  • api — FastAPI (Python) — auth, config, guest inventory, job enqueue
  • worker — same image, different command — schedule + restore pipeline
  • db — PostgreSQL
  • Optional Caddy/nginx — TLS terminator

Deploy target: Ubuntu LXC on Proxmox with Docker (nesting=1, keyctl, fuse as needed).

Core restore cycle (v1)

  1. Acquire global lock (fail or queue if busy).
  2. Resolve guest (VM or CT), host connection, latest PBS snapshot.
  3. Preflight: free ID in test pool; enough space on preferred restore storage (else fallback); PBS reachable.
  4. Restore to temp ID with unique identity (new MAC/UUID).
  5. Detach all network devices before start.
  6. Start guest; wait configurable boot delay (default ~60s).
  7. Capture evidence (VM: QMP screendump; CT: status/uptime proof).
  8. Stop + destroy/purge temp guest (always attempt cleanup in finally).
  9. Persist run record + artifact; send SMTP success/failure.
  10. Release lock.

Original guest stays online. No production shutdown for tests.

App modules / UI map

  • Dashboard — last runs, pass/fail, next scheduled, active lock status
  • Guests — inventory; exclude; per-guest schedule override; Run now
  • Runs — history, screenshot/evidence viewer, email resend
  • Hosts — API URL, token, SSH key, PBS/storage, test ID pool
  • Schedule — global cron + rotation policy
  • Notifications — SMTP presets, templates, test email
  • Users — admins, reset, 2FA
  • Settings — boot wait, retention, branding
  • Setup wizard — first-run flow

Security model

  • Proxmox API token with least privilege; documented ACL.
  • Dedicated SSH key for screendump / qm / pct.
  • Secrets encrypted at rest; tokens never shown in full after save.

Explicit future features (backlog)

  • OIDC
  • Webhooks / Slack / Discord
  • Guest probes (ping/HTTP)
  • Isolated bridge/VLAN mode
  • Per-host concurrency
  • Paid extras path (multi-tenant, HA worker, support packs)—not built in v1

Implementation phases

  1. Skeleton — Compose, Postgres models, auth + 2FA + password reset, shell UI with nav/theme
  2. Hosts — API client, SSH key helper, preflight checks, guest sync
  3. Worker — full VM cycle + CT cycle + global lock + cleanup guarantees
  4. Schedule + Guests UI — exclude, overrides, run now, rotation
  5. SMTP presets + run emails + Runs gallery
  6. Polish — setup wizard, LXC install docs, forum post, retention job

Out of scope for v1

  • Powering off production guests for tests
  • Restoring over the original VMID
  • Non-PBS backups
  • Concurrent restores
  • Marketplace billing / license servers
